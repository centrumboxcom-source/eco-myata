# ЕКО М’ЯТА — інструкція запуску

Це головний посібник власника. Новий посібник панелі: [ADMIN-GUIDE.md](ADMIN-GUIDE.md).

Підготовлено код підключення Supabase, Merchant Center та GA4/GTM. Без ключів Supabase сайт працює як демонстрація: зміни демонстраційної адмінки діють до перезавантаження. Публікація сайту сама по собі не підключає базу, банк або Google.

## 1. База даних

1. Створіть проєкт у [Supabase](https://supabase.com/dashboard), регіон Європи.
2. У **новій порожній базі** виконайте весь **supabase/bootstrap.sql** у SQL Editor. Файл містить міграції 001 + 002 + 003 в одній транзакції: таблиці, RLS, ролі, платежі, замовлення, статистику та bucket products.
3. Якщо вже виконували 001: зробіть резервну копію та виконайте **supabase/migrations/002_launch.sql (якщо ще не встановлена), потім supabase/migrations/003_catalog_editor.sql**. Не запускайте bootstrap або 001 повторно.
4. **supabase/seed.sql — необов’язкові демонстраційні товари й статті.** Замініть їх на фактичний асортимент, ціни, склад, алергени, харчову цінність, фото та залишки перед продажами.
5. Не вимикайте RLS. Фото JPG/PNG/WebP до 5 МБ читаються публічно; завантажує їх лише адміністратор.

Міграція 002 не видаляє замовлення чи товари. Якщо на старій базі унікальний індекс invoice_id повідомить про дублікати, спочатку звірте рахунки з банком.

## 2. Підключення сервера

Локально скопіюйте .env.example у .env.local. На хостингу додайте Environment Variables / Secrets:

| Параметр | Значення |
|---|---|
| NEXT_PUBLIC_SITE_URL | Основний HTTPS-домен; локально http://localhost:3000 |
| NEXT_PUBLIC_SUPABASE_URL | Project URL Supabase |
| NEXT_PUBLIC_SUPABASE_ANON_KEY | Публічний anon ключ |
| SUPABASE_SERVICE_ROLE_KEY | Серверний service_role того самого проєкту |
| NOVA_POSHTA_API_KEY | Ключ довідника Нової пошти |
| MONOBANK_TOKEN | Токен активного мерчанта Monopay |
| LIQPAY_PUBLIC_KEY / LIQPAY_PRIVATE_KEY | Ключі мерчанта LiqPay |
| INSTAGRAM_ACCESS_TOKEN | Необов’язковий токен професійного Instagram |

**Секретні ключі залишаються на сервері.** Не додавайте service_role/банківським ключам NEXT_PUBLIC_, не зберігайте їх у полях Google ID, не комітьте .env.local. Після зміни NEXT_PUBLIC_* потрібна нова збірка й публікація. Серверні секрети мають бути доступні й під час роботи сервера.

Усі бізнес-поля — назва, контакти, реквізити, домен, умови, GA4/GTM та verification — власник заповнює **в адмінці**. Вони зберігаються в settings.value. Ключі сервісів налаштовуються окремо на хостингу.

## 3. Вхід та адміністратор

Supabase → Authentication:

- Увімкніть Email provider, підтвердження email і власний SMTP.
- Site URL: основний HTTPS-домен.
- Redirect URLs: https://ВАШ-ДОМЕН/auth/callback та https://ВАШ-ДОМЕН/auth/callback?next=/account/reset. Для розробки додайте відповідні localhost:3000 URL.
- Confirm signup template: посилання `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`.
- Reset password / Recovery template: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery`.

Token hash підтримує відкриття листа на іншому пристрої. /auth/callback також підтримує PKCE.

Зареєструйте свій email на /account, підтвердьте його. У SQL Editor замініть ВАШ_EMAIL:

```sql
insert into public.profiles (id, role)
select id, 'admin' from auth.users where email = 'ВАШ_EMAIL'
on conflict (id) do update set role = 'admin';

select u.email, p.role
from public.profiles p join auth.users u on u.id = p.id
where p.role = 'admin';
```

Перевірте результат, увійдіть знову й відкрийте /admin. Покупці не можуть редагувати власні ролі.

## 4. Що заповнити в адмінці

1. **Категорії:** назва, порядок, батьківська категорія. Цикли заборонені. Перед видаленням перенесіть пов’язані товари й дочірні категорії.
2. **Товари:** реальні дані, ціна, залишок, головне фото й галерея. Архів приховує товар зі збереженням історії; «Активний» повертає його в каталог. Slug має бути унікальним, латиницею.
3. **Налаштування:** назва, SEO-опис, email, телефон, Instagram, поріг безкоштовної доставки.
4. **Дані продавця та умови:** ФОП/компанія, податковий ідентифікатор, адреса, доставка/строки/тарифи, повернення/винятки/відшкодування, умови продажу. Тексти публікуються на відповідних сторінках. Узгодьте їх із фактичною роботою бізнесу.
5. **Оплата та доставка:** увімкніть доступні способи. Для IBAN потрібні отримувач і рахунок.
6. **Google та аналітика:** основний HTTPS-домен без шляхів, Google ID, verification, фід. Домен використовується для SEO, sitemap, фіда та callback-ів; поле не купує домен і не налаштовує DNS.
7. **Блог:** тексти, обкладинки, slug, перемикач публікації. Чернетки приховані.
8. **Готовність до запуску:** усуньте відсутні налаштування. Перевірка бачить поля й наявність ключів; справність банків, SMTP і схвалення Google перевіряються окремо.
9. Відкрийте приймання замовлень після заповнення даних і перевірки каталогу. Увімкніть SEO-видимість перед публічним запуском.

Натискайте «Зберегти». Після збереження оновіть вітрину в іншій вкладці й перевірте результат.

## 5. Хостинг і домен

Потрібен Node.js 22.12+ (підходить 24 LTS) та хостинг Next.js із сервером/API routes. Static export не підходить.

```sh
npm ci
npm run typecheck
npm test
npm run build
npm start
```

Локальна розробка: `npm run dev`. Для стандартного Next.js-хостингу задайте install/build/start із команд вище. На VPS потрібні HTTPS reverse proxy, автоперезапуск процесу й журнали. Для standalone-контейнера скопіюйте public та .next/static у відповідні шляхи .next/standalone і запускайте `node .next/standalone/server.js`.

Sites-версія використовує OpenNext/Cloudflare. Звичайний Next.js-хостинг цього адаптера не потребує; технічні команди пакування наведені в README.

**Наявний Sites-перегляд приватний.** Для покупців, Googlebot і банків потрібен публічний HTTPS-домен без входу до Sites. Перевірте його у приватному вікні. Код не змінює аудиторію хостингу.

Домен в адмінці, NEXT_PUBLIC_SITE_URL, Supabase Site URL/Redirect URLs, Merchant Center та GA4 мають збігатися. DNS/HTTPS налаштовуються у вашого хостингу; інші домени перенаправляйте на основний.

## 6. Доставка, платежі та робота із замовленнями

**Нова пошта:** з NOVA_POSHTA_API_KEY завантажуються реальні міста/відділення/поштомати. Без ключа або при недоступності API покупець вводить адресу вручну. Укрпошта й кур’єр — також ручна адреса. ТТН створюється у перевізника й вноситься в адмінку; автоматичного створення немає.

Доставка сплачується перевізнику окремо, крім замовлень від налаштованого порогу безкоштовної доставки. Умови й тарифи на сайті та в Merchant мають збігатися.

**Monopay:** MONOBANK_TOKEN; callback https://ВАШ-ДОМЕН/api/webhooks/mono.
**LiqPay:** обидва ключі; callback https://ВАШ-ДОМЕН/api/webhooks/liqpay. Код використовує API v7 і SHA3-256.
**IBAN / при отриманні:** надходження перевіряє менеджер; для цього є кнопка в деталях замовлення.
**Apple Pay / Google Pay:** на платіжній сторінці банку, залежить від мерчанта й пристрою.

Повернення покупця на /payment/result саме по собі не означає оплату: потрібен перевірений callback. **Живі платежі не перевірені: ключів немає.** Виконайте погоджені банком тести успіху, відмови, повторного callback і повернення. LiqPay sandbox status не вважається реальною оплатою в цьому коді.

Замовлення одразу резервує залишок. Скасування повертає його один раз. Для оплаченої покупки спочатку поверніть кошти в банку, зафіксуйте повернення в панелі, потім скасуйте. Кнопка фіксації не переказує грошей.

Невизначений результат запиту до банку не створює автоматично другий рахунок. Перевірте кабінет банку; не скидайте payment_started_at без звірки. Поки рахунок очікує оплату, скасування заблоковане. Якщо callback втрачений, тільки після підтвердження банком анулювання адміністратор БД може виконати:
```sql
-- Лише коли банк підтвердив анулювання і неможливість подальшої оплати:
select public.record_payment('UUID_ЗАМОВЛЕННЯ'::uuid, 'failed');
```
Пізня оплата скасованого замовлення позначається payment_review: звірте й поверніть кошти або створіть нове замовлення.

Панель завантажує 200 останніх замовлень, «Завантажити ще» додає попередні. CSV експортує завантажений список. Статистика за 1/7/30 днів рахується за всіма замовленнями в БД, доба Europe/Kyiv. Дохід — оплачені або виконані без скасованих/повернених; це управлінський, не бухгалтерський показник.

Автоматичних банківських повернень, листів менеджеру та очищення прострочених резервів немає. Регулярно перевіряйте адмінку.

## 7. Google Merchant Center / Shopping

Фід: **https://ВАШ-ДОМЕН/merchant.xml**.

1. Створіть Merchant Center, вкажіть бізнес, підтвердьте й закріпіть домен. Для HTML meta tag вставте **лише content** у Google Site Verification. DNS-підтвердження — у провайдера домену.
2. У товарах задайте фактичні бренд і GTIN; якщо GTIN немає — бренд + MPN, коли вони існують. Не вигадуйте ідентифікатори. Перемикач наявності ідентифікаторів вимикайте лише для товарів, які справді їх не мають.
3. Додайте Google Product Category за потреби, увімкніть експорт перевірених товарів. Demo-товари за замовчуванням не експортуються.
4. Увімкніть приймання замовлень, SEO-видимість і загальний Merchant. Адмінка покаже помилки товарів. До завершення цих налаштувань /merchant.xml повертає 503.
5. Додайте джерело за URL, Україна, українська мова, UAH, регулярне отримання.
6. Налаштуйте в Merchant тарифи, строки, поріг безкоштовної доставки та повернення відповідно до сайту. Фід не розраховує тарифи перевізника.
7. Перевірте діагностику: сторінка, ціна/акція, залишок і фото збігаються. Фід читає актуальну БД, Google оновлюється за своїм розкладом.
8. Після схвалення товарів зв’яжіть Merchant із Google Ads та налаштуйте кампанії.

Є стабільні ID, XML-фід, GTIN/MPN, ціни/акції, фото/галерея, наявність, Product/Offer JSON-LD, canonical, sitemap та robots. **Інтеграція не гарантує схвалення Google.** Замініть demo-дані, використовуйте фото конкретного товару без рекламних написів, перевірте точність описів.

[Специфікація Google](https://support.google.com/merchants/answer/7052112?hl=uk).

## 8. GA4 або GTM

Оберіть **один** спосіб у «Google та аналітика».

### GA4 напряму

1. Створіть GA4 property і Web data stream.
2. Вставте G-…, режим GA4, збережіть.
3. Сайт сам надсилає page_view. У GA4 Enhanced measurement → Page views → Advanced settings вимкніть **Page changes based on browser history events**, щоб уникнути дублювання.
4. Вимкніть непотрібне автоматичне відстеження форм/пошуку. Наші ecommerce-події не передають контактів покупця чи query string.
5. Надайте згоду на cookies, перевірте Tag Assistant / Realtime / DebugView.

### GTM

1. Вставте GTM-…, оберіть GTM. Контейнер запускається після згоди на аналітику й маркетинг; налаштуйте consent checks усередині нього.
2. Додайте Google tag із G-…; `send_page_view=false`.
3. Custom Event **virtual_page_view** → GA4 Event **page_view**. Data Layer Variables: page_location, page_title.
4. Custom Event regex **^(view_item|add_to_cart|remove_from_cart|view_cart|begin_checkout|purchase)$** → GA4 Event name {{Event}}, ecommerce із Data Layer.
5. Виключіть account/admin з автоматичних тегів, вимкніть автоматичні history page views у GA4. Перевірте Preview та опублікуйте контейнер.

До згоди Google-теги не завантажуються. Вибір змінюється через cookies у футері. Для online purchase потрібна підтверджена оплата; для IBAN/при отриманні — прийняте замовлення (конверсія оформлення, не банківський облік). Є transaction_id і локальний захист від повтору. Не імпортуйте одну покупку двома способами в Ads як дві основні конверсії.

Це клієнтська аналітика: відмова, блокувальники або закриття сторінки до callback можуть зменшувати purchase. БД — джерело обліку замовлень. Measurement Protocol, Enhanced Conversions і рекламні кампанії не підключені.

[GA4 ecommerce](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce) · [Page views](https://developers.google.com/analytics/devguides/collection/ga4/views) · [Consent](https://developers.google.com/tag-platform/security/guides/consent).

## 9. Контроль перед рекламою

- Оновіть адмінку: збережені налаштування і товари залишилися.
- Магазин доступний без входу, видно контакти й фактичні умови.
- На телефоні широкий пошук і шапка залишаються зверху; «арахова» одразу знаходить «Арахісова».
- Перевірте реєстрацію, email, відновлення; покупець не бачить чужих замовлень та адмінки.
- Замовлення при отриманні + промокод: звірте суму, залишок, статус, CSV.
- Скасування повертає залишок лише один раз.
- Пройдіть тест банку, callback і повернення.
- Перевірте реальне відділення Нової пошти.
- Перевірте Merchant diagnostics і одну purchase у GA4.
- Увімкніть backup Supabase, резервування Storage; перевірте відновлення окремо.
- Налаштуйте моніторинг і обмеження частоти запитів /api/orders, /api/subscribe, /api/promo на хостингу. Не ставте CAPTCHA/вхід перед webhook-ами чи фідом.

```sh
npm run check:launch
```
Команда не змінює дані й не показує секрети. TODO означає незаповнені налаштування. Зелений результат не замінює тест банку.

## Межі перевірки

Тести покривають пошук, XML, GTIN, ціни/наявність, згоду, purchase, SQL-транзакції, купони, залишки, повтори, RLS, ролі, оплати/скасування, категорії, статистику та відгуки. SQL тестується у PGlite, не у вашому Supabase. Навантажувальний тест під рекламний трафік не проводився.

Власник додає домен, SMTP, ключі, банківський договір, реальні реквізити/умови та Google accounts. Email-розсилка, листи замовлень, автоматичні ТТН, повернення коштів і фіскальна/бухгалтерська інтеграція не реалізовані. Підписки зберігаються у subscribers; замовлення контролює менеджер.
